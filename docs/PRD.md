# Terminal AI Memo — Product Requirements Document

## エレベーターピッチ

**Terminal AI Memo** は、ターミナルで作業する開発者のための、AI付きメモ受信箱である。

作業中に浮かんだ疑問やアイデアを、保存先やタイトルを考えず `memo` と打つだけで記録できる。AIが後から過去のメモを検索し、要約、タグ、TODO、関連メモを提案するため、ユーザーは思考を中断せずに記録しながら、断片を再利用可能な知識へ育てられる。

Notionや一般的なメモアプリが「整理された情報を書く場所」であるのに対し、本アプリは**整理する前の断片を最速で捕まえ、後からAIでつなぐこと**に特化する。入力時にAIを待たせず、データはローカルに保存し、AIによる変更はユーザーの承認後にのみ反映する。

### 提供価値

- 作業画面を離れず、複数行の思考をすぐ記録できる
- 入力時にタイトル、タグ、保存先を決めなくてよい
- 忘れていた過去のメモとのつながりをAIが見つける
- 雑なメモからTODOや調査項目を取り出せる
- AIがなくても使え、AIに勝手に原文を変更されない

### 既存ツールとの違い

| 比較対象 | 主な用途 | Terminal AI Memoとの違い |
| --- | --- | --- |
| Notion | 整理・共有された情報の蓄積 | 整理前の入力に特化し、ターミナルから即座に記録する |
| 一般的なメモアプリ | 手動での記録と検索 | AIが複数メモを横断して関連、TODO、整理案を提案する |
| シェルのメモ／テキストファイル | 高速で単純な記録 | 検索可能な構造で保存し、後からAIで知識化する |
| AIチャット | その場での対話と回答 | メモをローカルに蓄積し、過去の自分の記録を継続的に参照する |

## 1. 概要

Terminal AI Memo は、作業中の思考や気づきをターミナルから素早く記録し、後からAIで整理・再発見できるローカルファーストのCLIメモアプリである。

ユーザーはグローバルコマンド `memo` を実行し、複数行のメモを入力する。入力時にはタイトル、保存先、タグなどの整理を要求しない。メモの保存は即座に完了させ、要約・分類・関連メモの探索といった時間のかかるAI処理は明示的な整理操作として後から実行する。

本プロジェクトは実用品の開発に加え、TypeScriptとLLMを使ったAIエージェントの設計を学ぶことを目的とする。書籍サンプル `minimal-coding-agent` は参照するが、本アプリは独立したリポジトリ、設計、実装を持つ。

## 2. 背景と課題

作業中に生まれる短い疑問、アイデア、TODOは、Notionなどの情報管理ツールへ整理して記録するほど形になっていないことが多い。アプリを開き、保存先やタイトルを決める操作は思考を中断させるため、記録自体を諦めることがある。

一方、雑なメモを大量に保存するだけでは、後から見つけられず価値が失われる。本アプリは「入力時の摩擦」と「保存後の整理」を分離し、記録時は極限まで軽く、必要なときだけAIエージェントが整理を支援する。

## 3. プロダクト原則

1. **入力を止めない**：メモ作成時にAI応答やネットワーク通信を待たせない。
2. **整理を求めない**：タイトル、タグ、保存先は入力時の必須項目にしない。
3. **ローカルファースト**：メモはユーザーの端末に保存し、AI機能なしでも利用できる。
4. **人間が最終決定する**：統合、編集、削除などの変更は提案として提示し、承認後に実行する。
5. **処理を説明できる**：AIが参照したメモと、提案理由をユーザーが確認できる。
6. **段階的に作る**：便利なCLIメモを先に完成させ、その上にエージェント機能を追加する。

## 4. 対象ユーザー

### 主なユーザー

- ターミナルを日常的に使うソフトウェア開発者
- コーディング中の疑問やアイデアを作業の流れを止めずに記録したい人
- AIエージェントのツール呼び出し、承認、検証、コンテキスト管理を実装しながら学びたい人

### 主な利用場面

- コーディング中に調査したい疑問が浮かんだ
- 実装アイデアを思いついたが、現在の作業を中断したくない
- ターミナルのエラーやコマンドに関する気づきを残したい
- 一日の終わりに断片的なメモを振り返りたい
- 過去に同じテーマについて考えたかを探したい

## 5. ゴール

### MVPのゴール

- どのディレクトリからでも `memo` を実行できる
- `memo` 実行後、複数行の文章を自然に入力できる
- 空行でEnterすると確定し、`Ctrl-C` でキャンセルできる
- 保存はネットワーク通信なしで素早く完了する
- 保存済みメモを時系列で確認できる
- 必要な場合のみ、現在のGitプロジェクト情報をメモへ付与できる
- 保存した未整理メモをAIに整理させられる
- AIがメモ検索・読解ツールを使い、関連する過去メモを必要に応じて参照できる
- AIがタイトル、タグ、要約、TODO、関連メモを構造化された提案として返す
- ユーザーが提案を確認し、承認した内容だけを保存できる
- 保存データを将来ほかの形式へ移行・出力できる

### 学習上のゴール

- CLIの入力・サブコマンド設計を理解する
- 永続化とドメインロジックを分離する
- LLMによる構造化出力を実装する
- エージェントによる検索、読解、提案のループを実装する
- 破壊的な操作に承認フローを設ける
- AIの提案をテスト・評価する方法を考える

## 6. 非ゴール

初期段階では、以下を対象外とする。

- Notionそのものを置き換える高機能な情報管理UI
- GUI、Web、モバイルアプリ
- 複数端末間のリアルタイム同期
- 複数ユーザーでの共有や共同編集
- 入力中のAI補完
- 初回からの複数LLMプロバイダー対応
- 完全自動でのメモの編集、統合、削除
- ベクトルデータベースを前提とした検索

## 7. ユーザー体験

### 7.1 複数行メモを作成する

```text
$ memo

New memo — submit with an empty line, cancel with Ctrl-C

ツールの実行結果も
コンテキスト圧縮の対象になる？

今度、長い出力で挙動を確認する。

Saved memo #42
```

要件：

- 改行を含む本文を入力できる
- 空の行でEnterすると入力を確定して保存する
- `Ctrl-D`によるEOFでも現在の入力を確定できる
- `Ctrl-C` では保存せず終了する
- 空の入力は保存しない
- MVPでは本文中に空行を含めない
- 保存成功時は短い確認のみ表示する
- 保存失敗時は原因と再試行可能な情報を表示する

### 7.2 一行メモを作成する

```bash
memo "あとでコンテキスト圧縮の挙動を確認する"
```

シェルスクリプトや素早い入力のため、一行引数による保存もサポートする。

### 7.3 最近のメモを見る

```bash
memo list
memo list --limit 20
```

新しい順にID、作成日時、本文の冒頭、プロジェクト名を表示する。

### 7.4 プロジェクト情報を付ける

```bash
memo -p
memo --project
```

現在地がGitリポジトリ内の場合、リポジトリルートからプロジェクト名を取得して保存する。Gitリポジトリ外ではプロジェクトを設定せず、その旨をエラーにはしない。

絶対パスの保存はプライバシーとノイズの観点からMVPの既定動作にしない。必要性が確認できた場合、後から `-d` / `--directory` として追加を検討する。

### 7.5 メモを検索する

```bash
memo search "コンテキスト圧縮"
```

MVPではローカルの全文検索を使用する。AIやネットワーク接続がなくても動作する。

### 7.6 AIで整理する（MVP）

```bash
memo organize
memo organize --today
memo organize <id>
```

AIエージェントは対象メモを読み、必要に応じて過去メモを検索・読解して、以下を提案する。

- タイトルとタグ
- 短い要約
- 類似・関連する過去のメモ
- メモから抽出したTODOや調査項目

提案の表示だけではデータを変更しない。ユーザーは提案全体を承認または拒否できる。承認した場合のみ整理結果を保存し、元の本文は変更しない。

複数メモの統合や削除はMVP後とする。MVPでは、AI処理が失敗した場合も元メモを保持し、再実行できる。

## 8. コマンド仕様

### MVP

| コマンド | 動作 |
| --- | --- |
| `memo` | 複数行入力を開始する |
| `memo "text"` | 一行メモを保存する |
| `memo -p` | Gitプロジェクト情報付きで複数行入力する |
| `memo list` | 最近のメモを表示する |
| `memo list --limit N` | 表示件数を指定する |
| `memo show <id>` | 1件のメモを全文表示する |
| `memo search <query>` | 本文をローカル検索する |
| `memo organize <id>` | 指定メモをAIで整理し、承認後に結果を保存する |
| `memo organize` | 未整理の最新メモをAIで整理する |
| `memo --help` | ヘルプを表示する |
| `memo --version` | バージョンを表示する |

### MVP後の候補

| コマンド | 動作 |
| --- | --- |
| `memo today` | 今日のメモを一覧・要約する |
| `memo edit <id>` | 既存メモを編集する |
| `memo delete <id>` | 確認後にメモを削除する |
| `memo export` | MarkdownまたはJSONへ出力する |
| `memo config` | 既定動作やモデル設定を管理する |

## 9. データ要件

### Memo

| フィールド | 型 | 必須 | 説明 |
| --- | --- | --- | --- |
| `id` | integer | Yes | ローカルで一意のID |
| `body` | text | Yes | 改行を保持した本文 |
| `createdAt` | datetime | Yes | 作成日時 |
| `updatedAt` | datetime | Yes | 更新日時 |
| `project` | text | No | Gitプロジェクト名 |
| `projectRoot` | text | No | 将来の利用を見越したGitルート。保存可否は設定可能にする |
| `title` | text | No | 手動またはAIが提案したタイトル |
| `status` | text | Yes | `raw`、`organized` などの整理状態 |

タグ、TODO、関連メモ、AI処理結果は元の本文と分離して保存する。AI処理の結果で元の本文を上書きしない。

### 保存方式

MVPではSQLiteを使用する。

理由：

- 単一ファイルでローカル管理できる
- 時系列表示、全文検索、更新に対応しやすい
- 小さなメモが増えてもファイルが散乱しない
- 将来のタグ、関連、AI処理履歴を表現しやすい
- JSONやMarkdownへのエクスポートを追加できる

macOSでの既定保存先は `~/Library/Application Support/terminal-ai-memo/memos.db` とする。`TERMINAL_AI_MEMO_DB_PATH` 環境変数で上書きでき、テストではインメモリデータベースを使用する。

## 10. AIエージェント要件（MVP）

エージェントには、必要最小限のツールを与える。

- `listMemos`：期間や状態で候補を列挙する
- `searchMemos`：キーワードでメモを検索する
- `readMemo`：指定したメモの全文を読む

タイトル、要約、タグ、TODO、関連メモはToolではなく、エージェントの構造化された最終出力とする。整理結果の保存もエージェントのToolにせず、CLIがユーザーの承認を得た後に通常のアプリケーション処理として実行する。

要件：

- 読み取り操作に個別承認を求めない
- 整理結果を保存する操作は承認対象とする
- ツール呼び出し回数に上限を設ける
- 参照したメモIDを結果に含める
- LLMの失敗や未設定時もAI以外のCLI機能を利用できる
- APIキーやメモ本文をログへ不用意に出力しない

## 11. 非機能要件

### パフォーマンス

- AIを使わないメモ保存は体感上即時に完了すること
- 通常規模のデータで `list` と `search` が対話的な速度で応答すること
- CLI起動時に不要なLLM SDKを初期化しないこと
- `organize` 以外のコマンドではLLM APIを呼び出さないこと

### 信頼性

- 保存処理はトランザクションを使用する
- 空メモや不正な引数でデータを作成しない
- AI処理の失敗によって元のメモを失わない
- スキーマ変更はマイグレーション可能にする

### プライバシーとセキュリティ

- 本文は既定でローカルにのみ保存する
- AI機能実行時は、外部モデルへ送信する内容を明示する
- APIキーをデータベースやログへ保存しない
- カレントディレクトリの絶対パスを既定で収集しない
- シェルコマンド実行ツールは初期のAIエージェントに与えない

### 可搬性

- macOSを最初の対応環境とする
- BunとTypeScriptを使用する
- コアロジックはCLI表示から分離し、将来Node.jsや別UIへ移植可能にする

## 12. 技術方針

- 言語：TypeScript
- ランタイム／パッケージ管理：Bun
- テスト：`bun test`
- 永続化：Bun組み込みの `bun:sqlite`
- UI：標準入出力を使ったCLIから開始
- LLM：MVPでは1プロバイダーに対応し、必要になってから抽象化する
- 配布：ローカル開発中はBunのリンク機能などで `memo` コマンドをグローバルに利用可能にする

本格的なTUIフレームワークは、入力体験に具体的な不足が見つかるまで導入しない。最初は複数行入力、保存、キャンセルが安定して動くことを優先する。

- [ ] `Ctrl-D`によるEOFでも現在の本文がSQLiteへ保存される

- [ ] 空または空白だけの本文は保存されない
- [ ] `memo "text"` で一行メモを保存できる
- [ ] `memo -p` でGitプロジェクト名を任意に記録できる
- [ ] Git管理外で `memo -p` を使ってもメモ保存は成功する
- [ ] `memo list` で新しい順にメモを確認できる
- [ ] `memo show <id>` で改行を保った全文を確認できる

- [ ] AIがタイトル、要約、タグ、TODO、関連メモを構造化して提案できる

## 14. 開発フェーズ

### Phase 1：入力と保存

- Bun／TypeScriptプロジェクトの初期化
- CLIエントリーポイント
- 複数行入力とキャンセル
- SQLiteスキーマと保存処理
- 一行入力

### Phase 2：参照と検索

- `list`、`show`、`search`
- Gitプロジェクト情報の取得
- グローバルコマンド化
- エラー表示とテストの拡充

### Phase 3：AIによる整理提案（MVP完成）

- LLM接続
- 構造化されたタイトル・タグ提案
- メモ検索ツールとエージェントループ
- 参照元を示す整理結果
- 承認後の反映

MVPはPhase 3までを完了した時点とする。

### Phase 4：再発見と外部連携

- 関連メモの提案
- 日次・週次レビュー
- Markdown／JSONエクスポート
- 必要性を検証した後のNotion連携

## 15. 成功指標

初期は利用回数よりも、以下を定性的に評価する。

- 作業中に思いついてから保存まで迷わず完了できるか
- Notionを開くほどではないメモを実際に残すようになったか
- 一週間後に `list` や `search` で必要なメモを見つけられるか
- AI整理が手作業を減らし、余計な修正作業を増やしていないか
- AI機能がなくてもメモツールとして使い続けられるか

## 16. 未決事項

- SQLite全文検索（FTS5）をMVPに含めるか、単純な部分一致から始めるか
- 本文中の空行を将来どの操作で入力可能にするか
- Gitルートの絶対パスを保存するか、プロジェクト名だけにするか
- AI整理結果をどの粒度で承認するか
- 最初に対応するLLMプロバイダー
- アプリ名と公開パッケージ名を `terminal-ai-memo`／`memo` で確定するか
